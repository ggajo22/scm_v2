# SPEC-ORDER-026 — Compact Summary

> v1.2.0 — plan-auditor 1차(FAIL 0.72) + 2차(FAIL 0.86) 리뷰 반영. AC 15개 → **17개**(AC-NET-015/016 신설), 변이 9개 → **11개**(M10/M11 추가), 위험 12건 → **17건**. 2차 감사는 Must-Pass 4개 전부 통과 + 수치 약 110개 불일치 0건 + 인용 어긋남 0건을 확인했고, 남은 차단 결함 1건(AC-NET-016의 RED 분류)을 (a) 단정을 바이트 동일성으로 재작성해 해소했다.

## 결함 (프로덕션 확정)

`_compute_cost_breakdown_for_rate`(`backend/order/serializers.py:31-73`)가 7개 비용 필드 전부를 **원시 `item.quantity`**와 **gross `obj.total_price`**로 계산한다. `Refund` 행이 있는 주문 **96건**(마진 렌더링 주문 2,847건 중)의 마진이 과대 계상된다. *(건수는 2026-08-17 원격 DB 스냅샷, UNVERIFIED — 구현 시점 재실측 권고)*

소비처 2곳이 이 함수를 공유하므로 한 곳을 고치면 두 화면이 함께 정정된다 — `OrderDetailSerializer`(상세 `결제 정보` 패널, `serializers.py:553`)와 `OrderListSerializer.get_margin_rate`(목록 `마진율` 컬럼, `serializers.py:279`).

**화면이 이미 자기모순**: 주문 `#37454`는 `최종 결제 금액 78.76`(프론트엔드가 환불 차감)을 표시하면서 `마진 37.22`(백엔드가 gross 116.04로 계산)를 나란히 보여준다.

## 왜 설계 선택이 아니라 결함인가

이 코드베이스는 8곳 이상에서 환불 순액화 관례를 적용하며 **비용 경로만** 건너뛴다. 정경 패턴: `purchase_order_views.py:334-342`(조인 키 `(order_id, shopify_line_item_id)`) + `:368`(`max(...,0)` 하한). 같은 파일 안의 선례: `serializers.py:179-191`(SPEC-ORDER-023). `serializers.py:165-178`의 주석이 명시한다 — "the cancellation signal lives in the Refund rows".

## 무엇을 만드는가

`serializers.py:31-73` **한 함수의 내부 산술만** 바꾼다. 시그니처·반환 키·메모이제이션·7개 게터·null 게이트 2곳 전부 무변경.

1. **수량 측**: 모든 라인아이템 집계(무게·권수·확정매입가)를 `max((item.quantity or 0) - refunded_qty[item.shopify_line_item_id], 0)`으로 계산.
2. **매출 측**: `max(total_price - Σ((subtotal or 0) + (total_tax or 0)), 0)` — 매칭 여부 무관 전체 환불 행 대상. 프론트엔드 `OrderDetailPage.tsx:159-163`와 **동일 공식**이라 두 값이 구조적으로 화해한다.

## 핵심 결정

- **[결정적] boolean 필터가 아니라 참 순액 산술.** `serializers.py:186-191`의 `trackable` 컴프리헨션은 순액을 포함/제외 판정으로만 쓴다(순액>0이면 원래 수량 전량 유지) — 출고/발주 판정엔 정답, 비용엔 오답. 수량 3 중 1건 환불이면 권수·무게·확정가가 **2/3로** 줄어야 한다. 이 변이는 재현 케이스 #37454로 **잡히지 않는다**(라인 단위 전량 환불이라 두 방식이 같은 답) → AC-NET-002(수량 3, 환불 1)가 유일한 방어선.
- **양쪽 순액화는 원자적.** 수량만 고치면 #37454 마진이 37.22 → 60.80으로 진실(23.52)에서 **더 멀어진다**(오차 13.70 → 37.28). 마일스톤 분할 금지(REQ-NET-013).
- **`purchase_status="order_cancelled"`는 범위 밖(명시적 비목표).** 그 행들은 `Refund`가 없어 매출이 안 내려간다 → 비용만 빼면 반대 방향으로 과대 계상. `Refund`만이 양쪽을 대칭으로 움직이는 신호. 해당 주문 **61건**. AC-NET-013이 이 비목표를 테스트로 고정한다.
- **쿼리 0 추가.** `refunds`는 두 뷰 모두 이미 prefetch(`views.py:59`, `:269`) → `obj.refunds.all()`만 쓴다. `purchase_order_views.py`의 `Subquery`/`OuterRef`를 옮기면 목록 페이지(50행)에서 +50 쿼리. AC-NET-009/010이 MUST-PASS.
- **`has_any_confirmed`는 순액화 전 평가**(REQ-NET-024). 유일한 확정 라인이 전량 환불돼도 7필드는 `null`이 아니라 `"0.00"`. 이유: 기존 null 게이트 의미 무변경 + 패널이 `0.00 − 0.00 = 0.00`으로 자기정합 유지 + `margin_rate`는 기존 매출 0 게이트로 이미 `null`.
- **과다 환불은 양쪽 하한 0.** 수량 하한 없으면 음수 무게에 기본료까지 부과. **매출 하한 없으면 음수/음수로 마진율 +100%가 표시된다**.
- **프론트엔드 무변경.** 새 백엔드 필드를 노출하지 않는다 — `DETAIL_SERIALIZER_FIELDS` 계약(`test_spec_023.py:39-58`)과 픽스처 2곳을 건드리는 비용이 목표에 기여하지 않는다. 중복 공식의 위험은 백엔드 단위 화해 단정(AC-NET-003)으로 고정.
