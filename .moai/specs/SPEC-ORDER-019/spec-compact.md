# SPEC-ORDER-019 압축 요약 — Daily Review 업로드 배포처 행 메모 유실

전체 문서: `spec.md`(EARS 요구사항 전문), `plan.md`(TDD 구현 계획), `acceptance.md`
(Given/When/Then + 판별력 명시), `research.md`(코드베이스·운영 DB 조사 근거, `file:line`
인용 전량 — 이 세션에서 직접 재검증).

## 문제

`UploadDailyReviewView`(`backend/order/purchase_order_views.py:1370`)는 각 행을 세 갈래로
보내고, 행의 메모는 `:1632`에서 `note = item.get("note")`로 한 번 읽힌다.

| 분기 | 위치 | 메모 저장 |
|---|---|---|
| CS | `:1644-1662` | **예** — `assignee="CS"`(`:1658`), `note_type=note_type`(`:1657`), 가드 `:1650` |
| 창고 | `:1675-1717` | **예** — `assignee`는 위치로 결정(`:1708`), 가드 `:1705` |
| **배포처(비창고)** | **`:1719-1756`** | **아니오 — `note`를 읽지도 않는다** |

배포처 분기 38줄 어디에도 `note` 식별자가 없다. `:1632`의 값은 조용히 버려진다 — 예외도,
`errors`(`:1439`) 항목도 없다.

**확인된 사례**: `Daily Order Review Template 20260713.xlsx`의 행
`Name=#35961` / `sku=9788936479497` / `선택=BOOXEN` / 메모 `"품절이지만 북센 시도"` →
업로드 후 `LineItemNote` 0건.

**규모**(운영 DB 실측 2026-08-13, `research.md` §2): 이 분기를 통과한 LineItem
(`confirmed_distributor`가 있고 창고 코드가 아님) **9,963건**(kyobo 4,887 / booxen 4,822 /
yes24 243 / 기타 11). **그중 어떤 노트든 가진 것은 12건.** 대조군 — 시스템 전체
`LineItemNote`는 355건(CS 216 / 한국창고 56 / 발주 42 / 미국창고 34 / 타출판사 7).

기재율은 DB로 알 수 없어(버려진 값은 어디에도 없다) 템플릿 파일을 직접 스캔했다 —
**완료, `research.md` §9.0**: 2026년 198개 파일, 배포처 행 56,637건 중 메모 보유
**1,172건(2.1%), 228종, 상투어 0건**. 현존 `LineItemNote` 355건의 3.3배가 유실된 셈.

## 솔루션

배포처 분기가 나머지 두 분기와 **동일한 방식으로** 메모를 저장한다. 프로덕션 코드 변경은
`:1719-1756` 안 약 10줄 + 주석 2줄이 전부다.

| 항목 | 결정 |
|---|---|
| 쓰기 경로 | 기존 `pending_notes`(`:1595`)에 append → 이미 존재하는 단일 `bulk_create`(`:1806-1807`)가 함께 처리. **쿼리 증가 0** |
| 공백 가드 | CS 분기의 `if note is not None`(`:1650`) 그대로 |
| `assignee` | `"발주"` |
| `note_type` | 모델 기본값 `""`(넘기지 않음) |
| `author` | `None` |
| 멱등성 | `_reorder_candidate_filter`(`:107-110`)에서 **상속**. 신규 dedup 없음 |
| 프론트엔드 | **변경 0** |
| 모델·마이그레이션 | 없음 |

## 설계 결정 요약

| 결정 | 내용 |
|---|---|
| A | **`assignee="발주"`.** `ASSIGNEE_CHOICES`(`models.py:242-247`) 4개 중 셋은 이미 임자가 있고(CS `:1658`, 한국창고/미국창고 `:1708`) 남는 하나가 의미상으로도 맞다. 선례 `ConfirmOrderView:1144`(계약 고정 `test_purchase_orders.py:1412-1430`). 결정적 부수 이점 — `LineItemNotesPage.tsx:343`의 탭이 `['CS','발주','타출판사']`이고 `:48`이 `assignee === tab`으로 나누므로 **프론트엔드 변경 0**. 기본값에 맡기면 `"CS"`(`models.py:277`)가 되어 발주 메모가 CS 큐(216건)에 섞인다. 기각 — 새 assignee 값 추가는 마이그레이션 + 프론트엔드 4곳 수정. |
| B | **`note_type=""`.** 전수 조사 결과(`research.md` §6) **`LineItemNote.note_type`을 DB에서 읽어 `purchase_status`를 유도하는 경로가 존재하지 않는다** — `_NOTE_TYPE_STATUS_MAP`(`excel_utils.py:614-622`)은 파싱 측에서 `'선택'` 열 라벨에만 적용된다(`:876`, `purchase_order_views.py:1646`). 실제 소비자는 셋뿐 — `views.py:314`(타출판사 엑셀 내보내기), `LineItemNotesPage.tsx:36`/`:41`(탭 라우팅), 배지 표시(`:77`, `:255`). 기각 — `"타출판사"`는 발주 메모를 출판사 엑셀에 새어 나가게 하는 **유일한 실피해 값**. `"발주요청"`/`"발주제외"`(`types/order.ts:88`)는 서버 측 무해하나 수동 입력 UI가 담당자 **의도**를 표현하려 만든 값이라 엑셀 자유 텍스트에 임의로 붙일 수 없다. |
| C | **멱등성은 상속하며 신규 dedup 없음.** 1차 업로드가 배포처 행의 LineItem을 PurchaseOrder에 연결하므로(`:1848-1888`) 2차에서 `_reorder_candidate_filter:109`의 `.exclude(purchase_status="unordered", purchase_orders__isnull=False)`에 걸려 후보에서 빠지고 행은 `:1637-1639`로 스킵된다. CS(`purchase_status` 변경 `:1646-1648`)·창고(`in_stock` `:1702`)가 중복을 안 만드는 이유와 **정확히 같은 이유**. 한계 3가지 명시 — (1) 내용 기반 dedup이 아니라 메모 수정 후 재업로드도 반영 안 됨, (2) 강제되지 않고 상속되므로 필터가 넓어지면 조용히 깨짐 → AC-MEMO-005가 잠금장치, (3) 같은 SKU의 새 LineItem은 자기 노트를 받음(정상). |
| D | **노트는 LineItem당 1건**(행당 아님). `lineitems_by_key`(`:1582-1590`)가 리스트를 값으로 가지며 기존 두 분기가 `for li in unordered_lis:`로 순회한다(CS `:1651`, 창고 `:1709`, `ConfirmOrderView:1139`). 그룹당 1건으로 만들면 형제 품목의 노트 화면(`views.py:259-261`)이 비어 보인다. |
| E | **프론트엔드 변경 0.** 경로 완결 확인 — `views.py:269-282`(`filter(is_resolved=False)` `:279`, assignee 필터 없음) → `serializers.py:79-97`(`:94-97`) → `LineItemNotesPage.tsx:306`/`:309` → `filterNotes:35-49`(`:48`). `is_resolved` 기본값 `False`(`models.py:273`). **부수효과(수용, 기존 특성)**: `filterNotes:38-46`이 CS/발주 탭에서 LineItem당 최신 1건만 보이므로 새 발주 노트가 기존 미해결 CS 노트를 가릴 수 있다. 업로드 CS 노트 → 배포처 노트 순서는 불가능(결정 C의 표)이나 **수동 입력 CS 노트** 후에는 가능. 창고 노트가 오늘 이미 똑같이 한다 → 후속 과제 2. |
| F | **요구사항은 열 이름이 아니라 파싱된 값에 결속.** 메모 출처 열이 형식마다 다르다 — 신규 템플릿은 `Status`, 레거시는 `메모`(`excel_utils.py:822-825`, 판별 `:803`). 둘 다 `:879`로 수렴한다. **주의**: 신규 템플릿의 `Status`는 과부하 열 — `선택="재고"`에서는 위치 해석자(`:1678`, `_WAREHOUSE_NOTE_LOCATION_MAP` `:1450-1454`), 그 외에는 자유 텍스트. 기존 픽스처가 배포처 행에 `"정상"`을 넣는다(`test_daily_review_upload.py:1325`, `:1350`, `:2207`) → 실제 파일도 상투어일 가능성 → `research.md` §9 조사. **설계는 이 답에 의존하지 않는다.** |
